## 🔴 CRITICAL GAPS

### Gap #1: **Double Parse Anti-Pattern**

**Location**: Generate.tsx → Study.tsx

**Problem**:
```typescript
// In useGenerationEngine.ts (line 220)
const loadResult = parseAndLoadContent(result.fullDocument, resultId);
if (loadResult.success) {
  navigate(`/study/${resultId}`);
}

// Then in Study.tsx (line 140)
const loadResult = parseAndLoadContent(result.fullDocument, subjectId, fallbackConcepts);
```

**Issue**: Content is parsed TWICE:
1. First in Generate page after generation completes
2. Again in Study page during hydration

**Impact**:
- Wasted CPU cycles
- Potential for inconsistent state if parsing logic differs
- Unnecessary delay in Study page load

**Why It Happens**:
- Generate page parses to validate content before navigation
- Study page doesn't trust that content is already loaded
- No way to signal "content already in store, skip hydration"

**Fix Needed**:
```typescript
// Option 1: Skip hydration if content already loaded
if (currentSession?.id === subjectId) {
  console.log('[Study] Content already loaded, skipping hydration');
  return;
}

// Option 2: Add flag to indicate fresh navigation
navigate(`/study/${resultId}`, { 
  state: { freshGeneration: true } 
});
```

### Gap #2: **Storage Manager Confusion**

**Location**: src/lib/storage/index.ts

**Problem**:
```typescript
async saveResult(_result: SavedResult): Promise<...> {
  // DISABLED: Concept storage is now handled by Lambda → DynamoDB
  return { success: true, path: 'lambda-managed' };
}
```

**Issue**: 
- `saveResult()` is called but does NOTHING
- Comment says "Lambda handles storage" but Lambda already saved it
- Generate page thinks it's saving, but it's a no-op
- Creates false sense of security

**Impact**:
- Confusing code - looks like it saves but doesn't
- If Lambda save fails, no fallback
- No error handling for storage failures

**Why It Happens**:
- Architecture changed from local storage to Lambda
- Old code path kept for "backwards compatibility"
- But there's nothing backwards compatible about a no-op

**Fix Needed**:
```typescript
// Option 1: Remove the no-op entirely
// Delete saveResult() and update Generate.tsx to not call it

// Option 2: Make it explicit
async saveResult(_result: SavedResult): Promise<...> {
  console.log('[StorageManager] saveResult is deprecated - Lambda handles storage');
  return { success: true, path: 'lambda-managed' };
}
```

### Gap #3: **Result ID Mismatch**

**Location**: Generate.tsx → Study.tsx

**Problem**:
```typescript
// In useGenerationEngine.ts (line 210)
const resultId = `${Date.now()}-${Math.random().toString(36).substr(2, 9)}`;

// But Lambda returns jobId from backend
// And Study.tsx expects sessionId from DynamoDB
```

**Issue**: Three different IDs in play:
1. **resultId** - Generated on frontend (timestamp + random)
2. **jobId** - Generated by backend Lambda (UUID)
3. **sessionId** - Stored in DynamoDB (UUID)

**Impact**:
- Study page has to do fuzzy matching to find the right session
- Hydration logic is complex because IDs don't match
- Potential for loading wrong session if IDs collide

**Current Workaround** (Study.tsx line 110):
```typescript
// Attempt 3: Check recent results (maybe ID mismatch)
result = recentResults.find(r => 
  r.id === subjectId || 
  r.subject === subjectId ||
  r.id.includes(subjectId) ||
  subjectId.includes(r.id)
) || null;
```

**Why It Happens**:
- Frontend generates ID before backend job starts
- Backend generates its own ID
- No synchronization between the two

**Fix Needed**:
```typescript
// Option 1: Use backend jobId as the source of truth
const result = await generateWithBackend(...);
const resultId = result.jobId; // Use backend ID
navigate(`/study/${resultId}`);

// Option 2: Pass frontend ID to backend
const resultId = generateId();
const result = await generateWithBackend(subject, callback, context, resultId);
```

### Gap #4: **Navigation Race Condition**

**Location**: useGenerationEngine.ts line 225

**Problem**:
```typescript
const loadResult = parseAndLoadContent(result.fullDocument, resultId);
if (loadResult.success) {
  setTimeout(
    () => navigate(`/study/${resultId}`, { replace: true }),
    UI_TIMINGS.DELAY_SHORT  // 300ms delay
  );
}
```

**Issue**:
- Artificial 300ms delay before navigation
- No clear reason for the delay
- User sees completed generation but can't interact yet

**Impact**:
- Perceived lag after generation completes
- User might click "Hide Generation" thinking it's stuck
- Unnecessary wait time

**Why It Happens**:
- Probably added to "let animations finish"
- Or to ensure store updates propagate
- But Zustand updates are synchronous

**Fix Needed**:
```typescript
// Remove the delay - navigate immediately
const loadResult = parseAndLoadContent(result.fullDocument, resultId);
if (loadResult.success) {
  navigate(`/study/${resultId}`, { replace: true });
}
```

### Gap #5: **Error Handling Disconnect**

**Location**: Generate.tsx → Study.tsx

**Problem**:
```typescript
// In Generate.tsx - if generation fails
setError(message || 'Generation failed.');

// But user is still on /generate/:subject page
// No automatic navigation to error state
// User has to manually click "Abort" or "Re-Initialize"
```

**Issue**:
- Error state is shown as overlay on Generate page
- But if user refreshes, they lose error context
- No persistence of error state
- No way to recover from error without retry

**Impact**:
- User loses error message on refresh
- Can't see what went wrong after page reload
- No error history or debugging info

**Fix Needed**:
```typescript
// Option 1: Persist error to localStorage
localStorage.setItem(`generation-error-${subject}`, JSON.stringify({
  error: message,
  timestamp: Date.now(),
  subject
}));

// Option 2: Navigate to error page
navigate(`/generate/${subject}/error`, { 
  state: { error: message } 
});
```

### Issue #8: **No Progress Persistence**

**Location**: Generate.tsx

**Problem**:
- If user refreshes during generation, progress is lost
- Has to start over from beginning
- No way to resume from checkpoint

**Current Workaround**:
- `useGenerationRecovery` hook reconnects to active jobs
- But only works if job is still running
- If job completed during refresh, user sees stale state

**Impact**:
- User loses progress on accidental refresh
- Can't see final result if they refreshed at 99%
- Frustrating UX

**Fix Needed**:
```typescript
// Store progress in localStorage
localStorage.setItem(`generation-progress-${subject}`, JSON.stringify({
  passes,
  progress,
  streamedConcepts,
  timestamp: Date.now()
}));

// Restore on mount
const savedProgress = localStorage.getItem(`generation-progress-${subject}`);
if (savedProgress) {
  const data = JSON.parse(savedProgress);
  // Restore state
}
```
